Fine-Tuning an Offensive-Security Assistant with LoRA

AI AGENT SECURITY February 2026 9 min read

Teach a small model your tradecraft, run it offline.

If you spend time attacking AI agents, it pays to build them too — you reason about a system differently once you've trained one. So I took an open-weight model and fine-tuned it into a small offensive-security assistant: feed it instruction/response pairs drawn from real recon and exploitation situations, and it learns to answer in that register. No API, no data leaving the box — a local model that speaks pentest.

This post is the full workflow with LLaMA-Factory: supervised fine-tuning (SFT) with LoRA, merging the adapters into a standalone model, and running it locally. It's a practical companion to the offensive-AI writing here — the same pipeline that ingests untrusted data is the one you retrain, and understanding fine-tuning is half of understanding data-poisoning and alignment-removal attacks against it.

// tooling

I got tired of running these steps by hand, so I built lazyLLaMA — a wrapper that automates this entire pipeline (env, dataset registration, training, merge, export). Everything below is what it does under the hood; if you just want the result, point it at your dataset and go.

Objective

Fine-tune an open-weight language model with LLaMA-Factory: supervised fine-tuning with LoRA, merge the resulting adapters into a single model, and run it on your own machine. We'll cover setting up the environment, configuring training, the common failure modes, merging, and executing the final model.

Setting up the environment

On Windows, WSL2 (Ubuntu) is the path of least resistance — you get GPU access without the pain of VM bridging. Keep dependencies isolated in a virtual environment:

python3 -m venv llamafactory_sft
source llamafactory_sft/bin/activate

Confirm your GPU is CUDA-capable (NVIDIA's CUDA GPU list), then install the toolkit and verify:

wget https://developer.download.nvidia.com/compute/cuda/12.2.0/local_installers/cuda_12.2.0_535.54.03_linux.run
sudo sh cuda_12.2.0_535.54.03_linux.run
nvidia-smi

Installing LLaMA-Factory

Clone the repo and install the core package plus the metrics extras:

git clone https://github.com/hiyouga/LLaMA-Factory.git
cd LLaMA-Factory/
pip install -e .
pip install -r requirements/metrics.txt

Sanity-check the install and dump your environment — this is the first thing to paste when something breaks:

Getting your dataset ready

This is where the "offensive-security" part lives. The model only becomes a pentest assistant if you feed it pentest thinking. Each record is an instruction/response pair — a situation and how a practitioner reasons through it. Save it as custom_dataset.json:

[
  {
    "Instruction": "During initial port scanning, you find TCP 64831 running an unknown service that returns HTTP-like responses. How do you proceed?",
    "Response": "Run service detection with nmap -sV. If it returns 'unknown', examine the fingerprint strings for HTTP headers (e.g. 'Location:', 'Set-Cookie:') — that indicates a web service, possibly a Go framework. Add the domain to your hosts file, browse to it, and enumerate endpoints and virtual hosts. Principle: unidentified ports returning HTTP-like data are usually web apps or APIs; treat them as such."
  },
  {
    "Instruction": "You discover a GoPhish instance with default credentials. After logging in, where do you look for internal domain names?",
    "Response": "Check 'Email Templates' — phishing templates link to fake domains (e.g. www.twitter.htb, www.paypal.htb). Extract every unique domain. Also check 'Landing Pages' and 'Sending Profiles'. Add them to your hosts file: these often resolve to the same server and reveal separate web apps or admin interfaces."
  }
]

Quality beats volume here — a few hundred sharp, opinionated pairs teach a small model far more than a heap of generic ones.

Registering your dataset

LLaMA-Factory discovers datasets through data/dataset_info.json. It supports Alpaca and ShareGPT formats; ours is Alpaca-style (instruction/response), so map the JSON fields explicitly:

{
  "custom_dataset": {
    "file_name": "custom_dataset.json",
    "columns": {
      "instruction": "Instruction",
      "response": "Response"
    }
  }
}

Supervised fine-tuning

The examples/train_lora/ directory has templates — copy one and adapt it rather than writing from scratch. I settled on Qwen3-1.7B (the 4B variants hit Out-Of-Memory on 4 GB during export). The training config:

### model
model_name_or_path: Qwen/Qwen3-1.7B
trust_remote_code: true

### method
stage: sft
do_train: true
finetuning_type: lora
lora_rank: 8
lora_target: all

### dataset
dataset: custom_dataset
template: qwen3_nothink
cutoff_len: 2048
max_samples: 1000
preprocessing_num_workers: 16
dataloader_num_workers: 4

### output
output_dir: saves/qwen3-1.7b/lora/sft
logging_steps: 10
save_steps: 500
plot_loss: true
overwrite_output_dir: true

### train
per_device_train_batch_size: 1
gradient_accumulation_steps: 8
learning_rate: 1.0e-4
num_train_epochs: 3.0
lr_scheduler_type: cosine
warmup_ratio: 0.1
bf16: true

The settings that matter on small hardware:

  • finetuning_type: lora — train small low-rank adapter layers instead of the full weights. This is what makes 4 GB viable.
  • lora_rank: 8 — adapter capacity. Higher rank = more capacity and more VRAM.
  • gradient_accumulation_steps: 8 — simulate a larger batch by accumulating gradients, without the memory cost of one.
  • bf16: true — mixed precision; cuts memory with little numerical cost.

Kick off training with:

llamafactory-cli train examples/train_lora/qwen3_lora_sft.yaml

When it finishes, saves/qwen3-1.7b/lora/sft/ holds the LoRA adapters (adapter_model.safetensors, adapter_config.json), a training_loss.png curve, and checkpoints. Important: at this point you have adapters, not a standalone model.

Merging the LoRA adapters

Merging fuses the adapters back into the base model to produce a single deployable model. One hard rule: never merge into a quantized base model. Start from examples/merge_lora/ and adapt:

### model
model_name_or_path: Qwen/Qwen3-1.7B
adapter_name_or_path: saves/qwen3-1.7b/lora/sft
template: qwen3_nothink
trust_remote_code: true

### export
export_dir: merged-qwen3-1.7b
export_size: 5
export_device: cpu
export_legacy_format: false

Then run the export:

llamafactory-cli export merge_config.yaml

The result lands in merged-qwen3-1.7b/ as a full model — LLaMA-Factory even drops an Ollama Modelfile alongside it, so you can hand it straight to ollama if you want (a topic for another post).

Running the model locally

Chat with the merged model directly:

llamafactory-cli chat --model_name_or_path merged-qwen3-1.7b

Why this matters for security

Two reasons this isn't just an ML exercise. First, it's capability: an offline assistant that speaks your methodology, with nothing leaving your machine. Second, it's understanding the attack — once you've watched a few hundred instruction/response pairs bend a model's behaviour, data-poisoning and fine-tuning-based alignment removal stop being abstractions. The same LoRA that teaches good tradecraft can teach the opposite; knowing the pipeline is how you reason about attacking it.

The whole thing is automated in lazyLLaMA. Point it at a dataset and it runs the pipeline end to end.
