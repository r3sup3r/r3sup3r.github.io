MCP Authorization — the Security Considerations, unpacked

AI AGENT SECURITY August 2026 11 min read

A valid token is not the same as an authorized token.

These are my notes on the Security Considerations section of the MCP Authorization spec — rewritten to teach, not just to reference. Almost every item comes back to one question: does this token belong here, and did a human actually consent to it being used this way? Keep that question in mind and the whole section stops being a list of rules and becomes one idea seen from nine angles.

The setup: OAuth 2.1 and three roles

MCP authorization is not a new protocol. It's OAuth 2.1 with MCP-specific rules bolted on top — and the spec is explicit that implementers MUST also follow OAuth 2.1's own Section 7 security considerations. MCP adds to them; it doesn't replace them.

Three roles carry the whole model. Learn these names or nothing else lands:

  • MCP client — the OAuth client. The app or agent asking for access.
  • MCP server — the OAuth resource server. It holds the protected tools and data. Crucially, it does not issue tokens — it only accepts them.
  • Authorization server (AS) — a separate party that issues tokens.

Fix that middle one in your head: the MCP server is a bouncer, not a ticket office. Every consideration below is really about making sure a token that shows up at the bouncer's door was actually printed for this venue.

Token audience binding — the keystone

The idea. A token should say who it's for, and the server should check. That's it. Everything else is a special case of this failing.

The mechanism. RFC 8707 Resource Indicators. The client MUST include a resource parameter naming the exact MCP server it wants access to, in both the authorization and token requests. The server MUST validate that the token it receives was issued for it — by checking the audience claim.

# the client's token request names the exact resource it's asking for
resource=https://mcp.example.com

The analogy. A concert ticket printed with the venue name on it. The door doesn't just check that your ticket is real — it checks it's their venue. Without that, a real ticket for any venue opens every door.

Attacker lens. Drop audience binding and any valid token from anywhere becomes a skeleton key. This is the root that the confused-deputy and token-passthrough problems both grow out of — so it's worth internalizing first.

The confused deputy — MCP's signature bug

The idea. An MCP server often sits in the middle: a resource server to its client, and an OAuth client to some third-party API it calls on your behalf (GitHub, a database, a SaaS). A middleman acting with delegated authority is a deputy. The confused deputy is when an attacker gets that trusted middleman to spend its authority for the attacker's benefit.

The attack (per spec). An MCP proxy server that uses a static client ID together with dynamic client registration. Because the proxy already holds cached consent for its static ID, the third-party AS may skip the consent screen. An attacker who obtains a stolen authorization code can then redeem it for access tokens without the user ever consenting.

The rule. MCP proxy servers using static client IDs MUST obtain user consent for each dynamically registered client before forwarding to third-party authorization servers.

The analogy. A hotel valet who will fetch any car for anyone who knows the valet's name. The vulnerability isn't a lock — it's the valet's standing trust relationship, exercised on the wrong person's say-so.

Token passthrough — never forward the token

The idea. When the MCP server needs to call an upstream API, the lazy move is to reuse the token the client already handed it. The spec forbids this outright, and it's the single most important operational rule in the section.

The rules. An MCP server MUST validate inbound tokens (OAuth 2.1 §5.2), MUST only accept tokens whose audience includes it, and MUST reject tokens that don't name it as the intended recipient. And when it acts as an OAuth client to an upstream API, that upstream token is a separate token issued by the upstream's own AS — the server MUST NOT pass through the token it got from the MCP client.

Why it matters. Passthrough collapses the audience isolation that binding just bought you. The upstream can no longer tell who is really calling, and a token minted for the MCP server suddenly works at services it was never scoped for. This is simply audience binding viewed from the exit door instead of the entrance.

Attacker lens. Find a server that forwards tokens and you can often ride a token issued for server A straight into API B. Passthrough is where "valid" quietly becomes "valid everywhere."

PKCE & authorization-code protection

The idea. The authorization code — the short-lived string the client swaps for a token — can be intercepted in transit. PKCE makes an intercepted code useless.

The mechanism. The client generates a secret verifier and sends only a hashed challenge up front; at exchange time it must prove it holds the original secret. Intercepting the code alone gets the attacker nothing.

The rules. MCP clients MUST implement PKCE with the S256 method, and MUST verify the AS actually supports PKCE before proceeding — by checking for code_challenge_methods_supported in the AS metadata. If that field is absent, the client MUST refuse to continue. (OAuth never defined a PKCE-discovery mechanism, so MCP pins it to metadata: no advertised support, no flow.)

Mix-up attacks

The idea. When a client talks to more than one authorization server and one of them is malicious, that AS can try to make the client hand it a code or token that an honest AS issued (RFC 9207).

The rule. Authorization Response Validation — the response has to tell the client which AS issued it, and the client checks that it matches the AS it actually started the flow with. Multi-AS setups are exactly where this bites.

Open redirection

The idea. A crafted redirect URI sends the user to a phishing site mid-flow.

The rules. Redirect URIs MUST be pre-registered with the AS; the AS MUST validate them by exact match (not prefix, not wildcard). Clients SHOULD use and verify the state parameter and discard any response whose state is missing or doesn't match.

Token theft & storage

The idea. A token stolen from the client's storage, or cached and logged on the server, lets an attacker make requests that look completely legitimate to the resource server.

The rules. Clients and servers MUST implement secure token storage (OAuth 2.1 §7.1). Authorization servers SHOULD issue short-lived access tokens to shrink the blast radius of a leak, and MUST rotate refresh tokens for public clients.

Attacker lens. Server logs and client caches are the first place I'd look — a token in a log file is a valid credential that no audience check will save you from once it's out.

Communication security

Short but non-negotiable: all authorization-server endpoints MUST be served over HTTPS, and every redirect URI MUST be either localhost or HTTPS. No cleartext anywhere a token or code can travel.

Client ID Metadata Documents — the new surface

A newer feature lets a client be identified by a URL that points to a metadata document the AS fetches. Anytime one server fetches a URL another party controls, new risks appear:

  • SSRF. The AS fetching an attacker-supplied metadata URL is a server-side request forgery primitive against the AS's own network. Authorization servers SHOULD treat that fetch as untrusted.
  • Localhost impersonation. These documents can't prevent localhost URL impersonation on their own, so the AS SHOULD warn on localhost-only redirect URIs and MUST clearly display the redirect hostname during authorization.
  • Trust policies. Authorization servers MAY apply domain-based allowlists for which metadata documents they'll accept.

The through-line

Read them back to back and the nine considerations converge on two words: audience and consent. Audience binding, no-passthrough, exact redirect matching, PKCE, mix-up validation — every one is the spec refusing to let a token be used somewhere, or by someone, it was never meant for. The confused-deputy rule is the same refusal aimed at the human in the loop: no silent consent.

So if you carry one sentence out of this: in MCP, "valid" and "authorized" are different words. A defender's job is to close the gap between them. An attacker's job is to find where it's still open — a forwarded token, a skipped consent screen, a redirect that matches by prefix, a code with no PKCE behind it. That gap is the whole game.
