The Open Door Is Not the Floor — SMB Null Session

Pentesting August 2026 14 min read AD Track · 01

AD track · attack 01 — null / anonymous SMB enumeration, run the whole way through: build the vulnerable box, break it, understand why it answered, then shut it and prove it's shut.

This is the first attack in the Active Directory track, and every post in it runs the same loop the creed asks for: build → understand → break. I make a lab box vulnerable on purpose, walk through the attack, stop to ask what exact condition let it work, then shut the door and confirm it's shut with more than one tool — and check what the defender would have seen. If you only ever met this attack as a command that pays out, the point here is to never again mistake the open door for the floor.

1 · What the attack is

Every Windows box exposes an administrative pipe share called IPC$ — Inter-Process Communication. It is not a file share: it exposes named pipes used for Remote Procedure Calls to remote services — the Server service, the Local Security Authority, the account manager, the service control manager, the task scheduler. Historically Windows let you connect to IPC$ with no username and no password — a null session — and then call the RPC interfaces SAMR (accounts) and LSARPC (policy/SIDs) to read, with zero credentials:

\PIPE\samr    → SAMR    (Security Account Manager, Remote)  → users, groups, RIDs
\PIPE\lsarpc  → LSARPC  (Local Security Authority)          → policy, SIDs, the domain SID

That leaks domain users and their RIDs, group memberships, the password policy (length, lockout threshold), the share list, and the domain SID. It's unauthenticated recon — the first thing you try against 445 — because everything it hands over feeds a later attack: the user list for spraying, the lockout policy so you don't lock accounts, the domain SID for ticket work down the line.

2 · Why it works (the mechanism)

Connecting to IPC$ anonymously maps you to the ANONYMOUS LOGON identity. Whether that identity can query SAMR/LSARPC is gated by LSA policy. Four things you have to understand — and the fourth is the one that explains most real-world surprises.

(a) RestrictAnonymous is not a simple on/off — it has three values:

RestrictAnonymousEffect
0Null sessions permitted with default permissions — fully exposed
1Blocks listing of accounts and shares, but still allows some anonymous connectivity — partial only
2Blocks all anonymous access (none without explicit anonymous permissions)

Alongside it: RestrictAnonymousSAM (block anonymous SAM enumeration) and EveryoneIncludesAnonymous (whether "Everyone" ACLs also grant the anonymous token).

(b) Authorization is layered — this is the key insight most people miss. A single "null session" passes through independent checks: SMB auth → IPC$ share access → opening the named pipe → and then each individual RPC function's own permission check.

anonymous bind ─▶ IPC$ access ─▶ open \samr ─▶ CALL a function
                                                   │
                     ┌─────────────────────────────┼─────────────────────────────┐
                     ▼                              ▼                              ▼
              QueryDisplayInfo               EnumDomainUsers               LsaOpenPolicy
              (nmap smb-enum)                (rpcclient)                   (rpcclient lsa*)
                     │                              │                              │
                 may be ALLOWED               may be DENIED                 may be DENIED

A host can let you open the null session and open the samr pipe, yet still deny the specific function you call. That's why rpcclient can fail while an Nmap script succeeds on the same box — they call different functions (LsaOpenPolicy vs QueryDisplayInfo) with different authorization requirements. Hold onto that; it comes back in every "is it safe?" decision below.

(c) Promoting a box to a Domain Controller silently loosens it. When a Windows Server becomes a DC, its config is changed to allow anonymous access to the samr, lsarpc and netlogon pipes. Most functions stay restricted, but some remain callable anonymously (e.g. NETLOGON's DsrGetDcNameEx2). So a hardened default member server and a DC do not behave the same — don't read the DC's extra exposure as a misconfiguration when some of it is the role.

(d) The legacy "Pre-Windows 2000 Compatible Access" group. In domains upgraded from older versions, Anonymous Logon / Everyone may still be a member of this built-in group — which re-grants anonymous read of directory objects even on an otherwise modern OS. This is the top real-world reason enumeration "still works" when it theoretically shouldn't.

Modern Windows locks most of this down by default — which is exactly why we deliberately weaken it in the lab, watch the attack, then put it back. That "build it broken on purpose" step is the part that teaches you which condition you're actually exploiting.

3 · Make it vulnerable

Two ways — command line and GUI. Do the GUI at least once: the policy names teach you what each control means, and naming the control is half of understanding the door.

Option A — PowerShell (elevated, on the Windows target)

Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" -Name RestrictAnonymous        -Value 0
Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" -Name RestrictAnonymousSAM     -Value 0
Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" -Name EveryoneIncludesAnonymous -Value 1

net user Guest /active:yes    # optional classic vector

Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Services\LanManServer\Parameters" `
  -Name NullSessionPipes -Value @("samr","lsarpc") -Type MultiString
Restart-Service LanmanServer -Force

To reproduce (d) on a real domain: add the anonymous principal to Pre-Windows 2000 Compatible Access via dsa.msc → Builtin, mimicking an upgraded domain.

Option B — via the Windows UI

Open secpol.msc → Local Policies → Security Options. Set each "Network access:" policy as below; every row writes the registry value the PowerShell sets.

Policy (Security Options)Registry valueMake vulnerableHarden
Do not allow anonymous enumeration of SAM accountsRestrictAnonymousSAMDisabledEnabled
Do not allow anonymous enumeration of SAM accounts and sharesRestrictAnonymousDisabledEnabled
Let Everyone permissions apply to anonymous usersEveryoneIncludesAnonymousEnabledDisabled
Restrict anonymous access to Named Pipes and SharesRestrictNullSessAccessDisabledEnabled
Named Pipes that can be accessed anonymouslyNullSessionPipesadd samr, lsarpc(empty)
Restrict clients allowed to make remote calls to SAMRestrictRemoteSam(leave unset)Administrators only

Enable Guest: same screen → Accounts: Guest account status → Enabled, or lusrmgr.msc → Users → Guest → untick "Account is disabled." (A DC has no local users — use dsa.msc; lusrmgr.msc is for SRV01/WS02.) Apply with gpupdate /force and restart the Server service so the pipe change takes effect.

The double-negative trap. The "Do not allow anonymous enumeration…" policies are negatives — to make the box vulnerable you set them to Disabled (you are disabling the protection). People flip this constantly. Read the name literally, then confirm the 0/1 it actually wrote.

Snapshot the VM as vuln-null-smb before you touch it from Kali, so you can replay this in seconds later.

4 · Run the attack (from Kali)

smbclient -N -L //172.16.10.10/                          # list shares anonymously
nxc smb 172.16.10.10 -u '' -p '' --shares
nxc smb 172.16.10.10 -u '' -p '' --users --groups --pass-pol
nxc smb 172.16.10.10 -u '' -p '' --rid-brute             # RID cycling (500=Admin, 501=Guest…)

rpcclient -U "" -N 172.16.10.10
  > querydominfo
  > enumdomusers
  > getdompwinfo
  > lsaenumsid

nmap --script "safe or smb-enum-*" -p139,445 172.16.10.10
enum4linux-ng -A 172.16.10.10

Why it worked: the anonymous IPC$ bind was accepted, and the loosened RestrictAnonymous* policy let ANONYMOUS LOGON reach the SAMR/LSARPC functions that read the account database. Nothing here is clever — the tooling is trivial. The only question worth anything is the one the tooling never makes you ask: why is this machine letting an unauthenticated caller run these functions at all?

Test with more than one tool. Because authorization is per-function (§2b), a single tool returning nothing is not proof the host is safe — it may just have called a restricted function while another pulls data fine. enum4linux-ng leans on RID-cycling via samr; rpcclient uses LsaOpenPolicy; Nmap uses QueryDisplayInfo. Run several before you conclude anything.

5 · Countermeasure

Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" -Name RestrictAnonymous        -Value 1   # =2 for strictest, test first
Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" -Name RestrictAnonymousSAM     -Value 1
Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" -Name EveryoneIncludesAnonymous -Value 0
Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Services\LanManServer\Parameters" `
  -Name NullSessionPipes -Value @() -Type MultiString
net user Guest /active:no
Restart-Service LanmanServer -Force

Then, for defence in depth: set Restrict clients allowed to make remote calls to SAM to Administrators only (Win10/2016+; blocks SAMR RID-cycling even for authenticated low-priv users); check the Pre-Windows 2000 Compatible Access group (dsa.msc → Builtin) and remove Anonymous Logon / Everyone if present — the number-one fix on upgraded domains; disable SMBv1 and use SMB 3.1.1; and push all of it by Group Policy (gpmc.msc) at the domain/OU, not host by host.

Legacy caveat (real world). Old multifunction printers, NAS boxes, and OT / line-of-business apps sometimes depend on null-session share enumeration. Jumping straight to RestrictAnonymous=2 can break them — test with =1 (partial) first, then tighten.

6 · Verify the fix (from Kali — the same attack should now fail)

nxc smb 172.16.10.10 -u '' -p '' --users         #  → STATUS_ACCESS_DENIED
rpcclient -U "" -N 172.16.10.10 -c enumdomusers  #  → NT_STATUS_ACCESS_DENIED
enum4linux-ng -A 172.16.10.10                     #  → users/groups empty

Run all three (per §4's false-negative warning). Access-denied across tools = confirmed. Snapshot hardened-null-smb.

Testing from a Windows box? Beware the false positive. When a Windows client connects with no explicit creds, SMB silently retries with the logged-on user's or the machine account — so a "null session" you think you made may actually be authenticated. Confirm with a Wireshark capture of the SMB Session Setup: check whether real credentials or a Kerberos ticket were sent. From Kali, -u '' -p '' genuinely sends anonymous.

7 · Detect it (blue-team view)

Anonymous enumeration is loud if you're watching. Monitor:

  • Event ID 4624 — Logon Type 3 (network) where the account is ANONYMOUS LOGON.
  • Event ID 5140 / 5145 — share access to \IPC$ with SubjectUserName = ANONYMOUS LOGON.
  • A spike of IPC$ tree-connects from one internal host fanning out to many targets — recon in progress.

Build the vuln, run the attack, and watch these fire in Event Viewer — it's the fastest way to feel why this attack is noisy, and it's the other half of understanding it. You don't know an attack until you can also see it from the defender's chair.

🎓 Lesson — the misconfiguration is the vulnerability

Most people meet this as "run enum4linux / nxc -u '' -p '' and the user list appears." In CTFs it appears every single time — so it gets filed as a law of nature, the way you "just start" a box, and you never ask the only question that matters: what condition is letting me read these accounts with no credentials?

On a default, modern, patched member server the answer is ACCESS_DENIED. So when the names do come back, that is the finding — not a free step. It works only because RestrictAnonymous* was loose, Guest was on, or Anonymous sits in Pre-Windows 2000 Compatible Access. Every one of those is a decision someone made or inherited, and every one is reportable. And a failure doesn't mean safe — authorization is per-function, so one tool's silence can be a false negative, and a "null session" from Windows can be a false positive. The command-runner reads one tool's output as truth; the mechanism-thinker knows which layer each tool is testing.

That's the whole creed on one box: I built the door open, walked through it, named the exact setting that let me, shut it, and proved it shut with more than one tool. The person who only ran the command is stuck the day it returns access-denied. The person who understands RestrictAnonymous, per-function authorization, and the Pre-Win2000 group knows exactly which door was open — and can write the sentence that's worth paying for.
