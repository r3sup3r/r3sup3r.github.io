A Goal Is Not a Method

Method August 2026 9 min read

When I started learning hacking, I thought the more commands I could memorize, the better I was.

I collected commands. I kept notes. I built cheatsheets. If I saw someone use a technique, I wanted to remember the exact syntax so I could reproduce it later.

For a while, that worked.

At least, it felt like it worked.

The problem was that I was learning attacks as commands instead of learning the conditions that made those commands work.

That distinction didn't really matter when I was working through predictable CTF boxes. If a technique worked once, there was a good chance it would work again. Eventually, the command stopped feeling like a technique and started feeling like the attack itself.

You see something. You run the command.

That's the habit I had to unlearn.

Because eventually you get a box that answers ACCESS_DENIED, and suddenly you have no idea what to do next.

Not because the target is particularly difficult. You just never stopped to learn what had to be true for the command to work in the first place.

That's what I want to talk about here.

A goal is not a method

Take a simple example:

Goal: enumerate domain users.

That is not the same thing as:

nxc smb <ip> -u '' -p ''

The first describes what you want to learn.

The second is one way of trying to get there.

That sounds obvious when written down, but I didn't always think about attacks that way.

A null SMB session is useful when anonymous access allows the relevant SAM/RPC operations.

If anonymous access is denied, the command failing doesn't mean that user enumeration is impossible. It means that particular route isn't available.

There might still be other ways:

GOAL: enumerate domain users
    ├── Null SMB session
    │     └── requires anonymous SAM/RPC access
    │
    ├── Authenticated RID enumeration
    │     └── requires usable credentials and sufficient access
    │
    ├── LDAP query
    │     └── requires a usable LDAP bind and appropriate directory access
    │
    └── Kerberos-based enumeration
          └── requires access to the KDC and a technique appropriate to the environment

The important part isn't memorizing that tree.

It's learning to think in terms of goals, methods, and conditions.

If one method fails, I still have the goal.

That's a small distinction, but it changes how you approach a target.

Instead of thinking:

"This command doesn't work."

you start thinking:

"What condition was this command relying on, and do I have another way of achieving the same objective?"

That is a much more useful question.

A failed technique can also tell you something about the target.

If an anonymous request gets ACCESS_DENIED, I haven't learned nothing. I've learned that this particular anonymous operation isn't available through this particular path.

The failure narrows the problem.

That's very different from simply moving on because "the command didn't work."

When an attack works, don't immediately move on

CTFs trained me to think about successful commands as progress.

You get the users. Great. Next step.

You get the hash. Great. Next step.

You get the shell. Great. Next step.

That mindset makes sense when the objective is to get through the box.

It becomes less useful on an actual engagement.

If anonymous enumeration works against a production system, the interesting part isn't just the list of usernames you received.

The interesting part is why an unauthenticated user was allowed to retrieve them.

That's potentially the finding.

The command itself isn't the valuable thing. The condition that allowed the command to succeed is.

That's a distinction I now try to make whenever something works unexpectedly.

Instead of:

"Nice, it works."

I try to ask:

"Why does it work here?"

Was it a default?
Was it a configuration choice?
Was it an intentional exception?
Is it expected for this system?
Does the same behavior exist elsewhere?
What information does it expose?
And, importantly, can I prove that the behavior is actually unauthorized?

Those questions turn a successful command into something useful for a report.

The five seconds spent running the command might be the easy part.

Understanding what those five seconds actually demonstrated is the real work.

A failed attack doesn't prove that the attack surface is safe

The opposite mistake is just as bad.

A command fails. You try it once. Nothing happens. So you write the technique off.

I've done that.

The problem is that tools don't necessarily test the same thing.

A server can allow a connection but restrict a particular operation. One tool might hit an RPC function that is blocked while another implementation reaches the information through a different path.

You can therefore get two completely different results from what, at a high level, looks like the same attack.

There is another problem: sometimes the tool isn't doing what you think it is doing.

Authentication state matters. Defaults matter. Fallback behavior matters. A tool may retry with credentials, negotiate a different authentication mechanism, or make additional requests that aren't obvious from the command you typed.

So if I get a failure, I try to understand the failure before deciding what it means.

Sometimes that means using another tool. Sometimes it means going lower level and looking at the protocol. Sometimes it means capturing the traffic. Sometimes it simply means reading the tool's documentation instead of assuming I know what it did.

The point isn't to run five tools every time something fails.

The point is to avoid making a much bigger claim than the evidence supports.

If all I know is that one command failed, then all I really know is that one command failed under those conditions.

That's not the same as proving the vulnerability doesn't exist.

Think about where the condition comes from

I've found it useful to separate the conditions behind an attack into three broad categories.

LayerWhat it meansTypical response
1. Protocol / designThe behavior exists because of how the protocol or technology worksManage exposure or compensate for the design
2. ConfigurationA setting determines whether the behavior is exposedChange the configuration
3. Operational realityThe environment makes an otherwise manageable behavior dangerousFix credentials, permissions, processes, or architecture

The distinction matters because the remediation is different.

Take Kerberoasting.

The KDC issuing a service ticket isn't, by itself, a misconfiguration. That's part of how Kerberos works.

The problem appears when the environment contains service accounts with passwords that can be cracked efficiently.

So there isn't necessarily a checkbox that says:

"Disable Kerberoasting."

You have to address the thing that makes the protocol behavior useful to an attacker.

That might mean stronger service-account passwords, managed service accounts, appropriate account configuration, and monitoring.

Compare that with something like anonymous access being unnecessarily enabled.

There, the underlying protocol may support the behavior, but a configuration decision determines whether an unauthenticated attacker can use it.

That's a different problem and therefore a different remediation.

This is why I don't like treating "the attack" as a single thing.

The technique is only one part of the equation.

You also need to understand what makes it possible.

This matters a lot more on an engagement

A CTF asks:

Can you get the flag?

An engagement asks a different question:

What can an attacker do, why can they do it, what does it mean for the organization, and how should it be fixed?

Those are not the same job.

If I write:

"Ran enum4linux and obtained domain users."

I've documented an action.

I haven't really documented a finding.

A better explanation would be something like:

"The host permits unauthenticated enumeration of domain accounts through the exposed SAM/RPC interface. An unauthenticated user was able to retrieve account information without valid domain credentials."

Now the important part is no longer the command.

It's the security condition.

That's what another tester needs to reproduce.

That's what the client needs to understand.

And that's what the remediation needs to address.

It also forces me to be more careful with negative results.

If I haven't actually established that something is impossible, I shouldn't write that it is.

"Not observed with this technique" is sometimes a much more accurate statement than "not vulnerable."

That may sound like report-writing detail, but it changes how you test in the first place.

The four questions I try to ask now

I've ended up with four questions that I try to apply to almost every technique.

1. What is this actually doing?
   Understand the mechanism, not just the syntax.

2. What condition makes it work?
   What does the target have to allow?

3. Where does that condition come from?
   Protocol design, configuration, or operational reality?

4. If it fails, what did I actually learn?
   Don't turn one failed command into a conclusion about the whole attack surface.

The first question stops me from treating commands as magic.

The second makes the command conditional.

The third helps me understand what the eventual remediation might look like.

The fourth stops me from throwing away useful information when something doesn't work.

That's the part I wish I'd understood earlier.

I don't need to memorize every command.

I need to understand what I'm trying to accomplish, what assumptions a technique makes, and what those assumptions tell me about the target.

A command is just one implementation of an idea.

Once you understand the idea, you can change the command. You can change the tool. You can change the protocol you're testing. You can even abandon the original technique entirely and find another route to the same goal.

That's a much stronger position to be in than knowing fifty commands by heart.

Putting this into practice

I want to apply this way of thinking to an Active Directory pentesting series.

Rather than making another collection of commands to memorize, I'm going to take the common AD techniques one at a time and look at what is actually happening underneath them.

For each technique, I'll try to answer the same questions:

What is the goal?
What does the technique actually do?
What conditions does it require?
Why does it work when it works?
What does a failure actually tell us?
How can we verify the result?
What does the finding look like from a reporting perspective?
How would you remediate the underlying condition?

The first one is null-session SMB enumeration.

It's a good place to start because it's easy to learn the command and completely miss the more important lesson behind it.

The command is not the attack.

The command is one way of testing whether a particular condition exists.

Once you start looking at techniques that way, a successful command gives you something to investigate, and a failed command gives you something to reason about.

That's the habit I'm trying to build.

Not memorizing more commands.

Understanding the conditions behind them.
