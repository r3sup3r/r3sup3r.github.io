The RAG → MCP → A2A Attack Surface

AI AGENT SECURITY August 2026 11 min read

One pipe, not three products.

RAG, MCP, and A2A look like three separate technologies. From a security seat they are one thing: a single, continuous path that untrusted data walks from the open internet to the inside of your systems — and then to someone else's.

Those three acronyms describe how nearly every serious AI agent in production is built today. Retrieval-Augmented Generation (RAG) feeds a model external documents so it can answer with current or private knowledge. The Model Context Protocol (MCP) lets that model call tools — read files, query databases, fetch URLs. Agent-to-Agent (A2A) lets one agent hand work off to another. Stack them and you have the reference architecture for the modern agent.

The security problem sits at the center. The model has no privilege separation. Everything that reaches its context window — your instructions, a retrieved document, a tool's output, another agent's message — arrives as the same undifferentiated text, and the model acts on all of it with equal authority. So these are not three isolated surfaces to harden separately. They are one pipe, and untrusted data flows through it end to end.

Every arrow is a place where untrusted data becomes trusted. Those arrows are the bugs. Walk the pipe one stage at a time.

Stage 1 — RAG: the intake

RAG's job is to pull relevant external content into the prompt so the model can use it. That content is, by definition, not written by you — it's a web page, a wiki article, a support ticket, a PDF a user uploaded. The instant it lands in the context window it is read with the same authority as your system prompt.

This is indirect prompt injection, and RAG is its delivery mechanism at scale. An attacker who can influence a single document that might get retrieved can plant instructions the model will later obey — no access to your servers required, just access to something your retriever ingests. The assumption that breaks is the oldest one in this field: that retrieved text is data, not instructions. In an LLM, that distinction does not exist.

Stage 2 — MCP: injection becomes action

On its own, an injected instruction is a curiosity — it can make the model say something. MCP is what turns it into an action. MCP is a JSON-RPC 2.0 protocol that exposes tools to the model: a filesystem reader, a shell, an HTTP fetcher, a database client.

Once the model can call tools, the instruction planted in Stage 1 can trigger one — and the classic bug classes are back, reached through the model instead of through a request. A fetch tool becomes SSRF (point it at cloud metadata). A shell tool becomes command injection. A file tool becomes path traversal. MCP also adds its own surface: the tool descriptions the model reads on every call are themselves attacker-controllable text — tool-description poisoning, or "line jumping." The assumptions that break here: that a tool argument is just an argument, and that the model only calls tools the user intended.

Stage 3 — A2A: the blast radius

A2A lets an agent delegate to another agent. The output of a compromised agent — or the compromised agent itself — now becomes input to a peer that trusts it. A poisoned document from Stage 1, escalated to a tool call in Stage 2, becomes a foothold that spreads across an agent mesh in Stage 3.

This is the confused deputy problem at the network level: agent B acts on agent A's behalf, with A's privileges, on the strength of a message A had no reason to trust. The assumption that breaks: that a peer agent's messages are trustworthy because they came from "inside."

The lethal trifecta, by construction

Simon Willison's framing says an agent is dangerous when it holds all three of: access to private data, exposure to untrusted content, and the ability to communicate externally. The uncomfortable thing about this architecture is that it has all three by default. RAG supplies private data and untrusted content. MCP and A2A supply the ability to act and to reach outward. You don't assemble the trifecta by accident in this stack — it's the baseline. That is why the pipeline is inherently dangerous, not because any single component is buggy.

Where the bugs will be

This is a map, not a disclosure — there are no CVEs in this post. But a map should make predictions. Before I open any repository built on this stack, these are the three things I check first, in this order:

  • RAG stores that don't isolate tenant data — one user's uploaded document retrieved into another user's context.
  • MCP servers that shell out or fetch with model-controlled arguments and no allowlist — the mcp-remote-class bug family.
  • A2A links with weak or no authentication — trust granted by network position instead of identity.

Every one of those is a trust boundary drawn in the wrong place, and none of them requires understanding a transformer. That's the whole point: this is an application-security problem wearing an AI costume, and the systems knowledge a pentester already has is most of what it takes to find these.
